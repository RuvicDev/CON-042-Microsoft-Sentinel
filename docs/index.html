¿Qué es y para qué sirve?

El conector Microsoft Sentinel permite que el agente de Ruvic gestione incidentes de seguridad y consulte eventos en tu workspace de Sentinel — listar incidentes, actualizar su estado, y ejecutar consultas KQL.

Una vez configurado, puedes pedirle al agente cosas como:

  • "¿Qué incidentes de severidad alta están activos?"
  • "Cierra el incidente X, ya fue investigado."
  • "¿Qué alertas de seguridad hubo en los últimos 7 días?"

Operaciones soportadas:

OperaciónQué hace
cybersecurity.list_incidentsLista incidentes, con filtros por estado y severidad
cybersecurity.update_incidentActualiza estado, severidad o propietario de un incidente
cybersecurity.execute_kql_queryEjecuta una consulta KQL contra el workspace
Dos APIs de Azure combinadas Este conector combina la API de administración de Azure (para incidentes) y la API de Log Analytics (para consultas KQL) de forma transparente — no necesitas configurarlas por separado, solo los datos del workspace.

Prerrequisitos

  • Un workspace de Microsoft Sentinel ya desplegado en Azure.
  • Acceso a Azure Portal (Microsoft Entra ID) para registrar una aplicación.
  • Permisos para asignar roles de IAM sobre el workspace (o alguien que pueda hacerlo por ti).

Configuración en el fabricante

  1. Registra una aplicación en Azure AD. Azure Portal → Microsoft Entra ID → App registrations → New registration.
  2. Genera un Client Secret. En la app registrada: Certificates & secrets → New client secret. Cópialo de inmediato, solo se muestra una vez.
  3. Otorga los roles de IAM sobre el workspace. En el recurso del workspace de Sentinel: Access control (IAM) → Add role assignment → asigna "Microsoft Sentinel Responder" y "Log Analytics Reader" a la aplicación.
  4. Anota los identificadores del workspace. En la vista de resumen (Overview) del workspace, copia el Subscription ID, Resource Group, nombre del workspace, y el Workspace ID (el GUID, distinto del nombre).

Permisos requeridos

Rol de IAMPara qué lo usa el conector
Microsoft Sentinel ResponderNecesario para list_incidents y update_incident
Log Analytics ReaderNecesario para execute_kql_query

No otorgues "Microsoft Sentinel Contributor" completo ni roles de administrador de la suscripción — este conector no crea ni elimina incidentes ni reglas de detección.

Configuración en Ruvic

Entra a Settings → Conectores, busca la tarjeta Microsoft Sentinel y pulsa Configurar.

Completa los datos de la App Registration (Tenant ID, Client ID, Client Secret) y los del workspace (Subscription ID, Resource Group, nombre, y Workspace ID).

Guarda y pulsa Probar conexión.

Verificación

  1. Test de conexión exitoso.

    El botón Probar conexión debe responder: "Conexión exitosa al workspace [nombre]".

  2. Prueba mínima con el agente.

    Pide algo de solo lectura primero:

    "¿Qué incidentes activos hay?"

Solución de problemas

Mensaje / síntomaCausa probable y solución
"Azure AD rechazó la autenticación"Tenant ID, Client ID o Client Secret incorrectos, o el secret expiró.
"Permisos insuficientes" (HTTP 401/403)Falta asignar el rol de IAM correspondiente (Microsoft Sentinel Responder o Log Analytics Reader) a la app sobre el workspace.
"No encontrado" al listar/actualizar incidentesRevisa que Subscription ID, Resource Group y nombre del workspace sean exactamente correctos.
execute_kql_query falla pero list_incidents funcionaEl Workspace ID (GUID) puede estar mal — es distinto del nombre del workspace, verifícalo en la vista Overview de Azure Portal.

Preguntas frecuentes y notas de seguridad

¿El agente puede crear o eliminar incidentes?

No. Solo puede listar, actualizar campos de incidentes existentes, y consultar con KQL.

¿Por qué se necesitan dos roles distintos?

Porque Sentinel combina dos servicios de Azure con permisos independientes: la gestión de incidentes vive en la API de administración, y las consultas KQL usan la API de Log Analytics.

¿Dónde queda guardado el Client Secret?

Como secreto en el almacén de credenciales de la plataforma. La interfaz nunca vuelve a mostrarlo.

¿Qué hago si el secret se compromete?

Ve a Azure Portal → la App Registration → Certificates & secrets, elimina el secret comprometido, genera uno nuevo, y actualízalo en el formulario del conector.

Buenas prácticas Otorga solo los roles mínimos necesarios; ponle fecha de expiración al Client Secret y renuévalo periódicamente; y confirma la intención del usuario antes de cerrar o modificar un incidente real.
